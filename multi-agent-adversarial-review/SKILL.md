# 多 Agent 对抗式审查

对代码变更、diff、commit、分支或设计文档进行对抗式审查。审查由强制的独立 subagent 分两轮执行，交付物是完整审查报告。本 skill 绝不修改代码。

## 何时使用

- 用户要求对抗式审查、多 agent 审查、独立意见，或挑战某个结论/严重度。
- 用户明确要求 N 个独立 agent 或挑战者 agent。
- 一个变更或设计即将被信任、合并或发布，需要基于证据的严重度验证。

不要将本 skill 用于单次普通代码评审，或与用户交互式讨论方案。

## 核心不变量

1. **强制 subagent，无降级路径。** 每轮审查都必须经过独立 subagent。若 subagent 不可用，停止并告知用户审查无法执行，等待后重试；绝不静默降级为单上下文审查。
2. **独立性是核心。** 第一轮评审者收到同一原始产物 + 一个差异化视角，绝不收到主 agent 的发现、怀疑或倾向。用户给出的假设不全局注入，只分配给一个评审视角做专项验证。
3. **挑战者攻击结论，而非只看代码。** 第二轮挑战者收到第一轮结论清单 + 代码上下文片段，绝不收到评审者的完整推理。挑战者可读代码核实声明，且永远不知道哪条结论来自用户。
4. **绝不修改代码。** 只交付报告。若用户要求修复，说明修复超出本 skill 范围，建议另开任务。
5. **严重度需要证据。** 无证据即理论风险，绝不打 P0/P1/P2 标签。降级和驳回必须说明理由。

## 流程

### 第 0 步：收集范围并确定强度

1. 确定审查对象：diff、commit、分支或设计文档。记录基线：当前工作区状态、相关文件、对象身份（commit 短 hash / 分支名 / 文档路径）。
2. 确定评审数与挑战者数：
   - 用户指定了规模（评审数、挑战者数或每视角冗余度 R），则用用户指定值。
   - 否则由主 agent 快速扫描决定：小型/局部变更默认 3 个视角；复杂/高风险变更（并发、状态机、网络、回调、资源生命周期、核心路径）默认 5 个视角。挑战者数默认：3 视角 → 1 个；5 视角 → 2 个。
   - 冗余度 R：默认每个视角 1 个评审 agent。用户可设置 R 最高为 3（最高强度）。第一轮评审总数 = 视角数 × R。
3. 在报告元信息块中说明所选强度及理由。任何时刻 subagent 不可用：停止、报告、等待，不要在没有 subagent 的情况下继续。

### 第 1 步：准备原始产物与视角

1. 提取原始产物：完整 diff/commit 文本，或完整设计文档，加上相关文件路径列表和客观背景（模块名、用户所述变更意图）。
2. 从推荐视角列表中选择视角，适配变更。每个评审 agent 分配一个视角。若用户给出假设，将其作为一个专项视角分配给一个评审 agent（R>1 时该视角有 R 个评审）。其余评审 agent 保持完全中立。
3. 绝不把主 agent 自身的发现、怀疑或提示传进评审 prompt。不暗示"已知存在严重问题"。

推荐视角列表（可自由适配；新增视角记入报告）：

- 正确性与回归
- 并发与生命周期
- 错误处理与边界
- 契约与兼容性
- 安全与资源
- 性能与可观测性

### 第 2 步：第一轮 — 独立评审者

1. 派生 R × 视角 个评审 agent。每个收到：原始产物、一个分配视角、证据格式要求（代码位置、触发路径、初判严重度），以及先陈述"我理解的范围"再给发现的指令。
2. 所有评审者互不可见；报告完成前绝不把某个评审者的输出共享给另一个。
3. 每条发现必须标注可点击的代码位置，格式为 `<文件路径>:<起始行>`，跨行区间用 `<文件路径>:<起始行>-<结束行>`（如 `src/foo.c:42-58`）；位置基于审查基线（当前工作区或 diff 上下文）说明。设计文档引用 `<文档路径>:<小节标题>（第 <行号> 行）`。无法标注位置的发现直接驳回。

### 第 3 步：第二轮 — 挑战者

1. 派生挑战者（3 视角 → 1 个；5 视角 → 2 个；或按用户指定）。挑战者互不可见。
2. 每个挑战者收到：第一轮结论清单（每条含代码位置、触发路径、初判严重度、证据）+ 代码上下文片段（作为中性证据索引，片段必须标注文件路径与行号）。绝不包含评审者完整推理。绝不标注任何结论来自用户。
3. 挑战者任务：攻击严重度、攻击证据链完整性、寻找被忽略的路径、寻找结论间矛盾。每条攻击必须有代码或逻辑依据。挑战者可打开文件、查更多位置、用 git 历史核实声明；挑战者发现"关键路径不在提供的片段中"本身就是一个有效的对抗发现。
4. 预选片段是降低成本的索引，不是约束，且不得携带倾向性描述。

### 第 4 步：有界辩论直至共识

1. 对每个攻击点，在被攻击发现对应的评审者与发起攻击的挑战者之间逐条辩论。每个攻击点最多 2 轮往返（攻击 → 反驳 → 反攻/接受）。一次只辩一个攻击点，不批量混辩。
2. 共识 = 双方对严重度和证据链是否成立达成一致。评审者被说服则相应降级/升级；挑战者被说服则维持原判。
3. 达到上限仍未共识：将该发现标记为**争议项**，记录双方最终立场，升级主 agent 做有理由的裁决。若代码证据也无法判定，降级为"需运行验证"并明确列出。绝不静默合并争议。

### 第 5 步：产出报告

将报告写为审查对象工作区中的独立 Markdown 文件，命名 `adversarial-review-<对象标识>-<YYYYMMDD>.md`，对象标识为 commit 短 hash、分支名或文档名。若目标工作区不可写，写入当前可写目录并给出绝对路径。

报告结构：

1. **范围与基线** — 审查对象、基线状态、强度与规模（视角数 × R + 挑战者数，是否用户指定）。
2. **视角分配记录** — 分配了哪些视角、为什么、新增了哪些。
3. **评审发现** — 每条含代码位置（文件 + 行号区间，格式见报告模板）、触发路径、证据、初判严重度。
4. **对抗记录** — 每个攻击点、辩论轮次、共识 / 争议 / 驳回及理由。
5. **最终分级表** — 合并后的 P0/P1/P2/理论风险，每条可追溯到来源（评审者 / 挑战者 / 主 agent）。争议项单独标注。
6. **未验证项** — 依赖运行验证的结论、未运行什么、为什么。
7. **裁决摘要** — 最终结论和建议的下一步（仅评审意见）。

外加两个固定小节：

- **用户假设裁决** — 三态：证实 / 证伪 / 证据不足，附专项评审者的证据链。挑战者可像攻击其他发现一样攻击该裁决。
- **范围边界** — 审了什么、明确没审什么（例如：仅静态审查，未做运行验证；未覆盖模块 X）。

### 并发与失败处理

1. 环境允许时并行派生评审者与挑战者。遇到并发限制或瞬时派生错误：**不跳过**该 agent。退避重试（如 30 秒），最多 3 次，记录每次重试。
2. 重试耗尽：停止审查并向用户报告失败（哪个 agent 失败）。不得产出声称覆盖完整但缺 agent 的报告。
3. 等待 agent 期间，不预先起草会偏置最终报告的发现或结论。

## 严重度定义

- **P0** — 真实路径上阻塞、数据损坏、崩溃或安全问题。
- **P1** — 明确缺陷，存在绕行方案。
- **P2** — 边界/健壮性问题。
- **理论风险** — 未找到可执行路径；在证据出现前保持理论。
- **降级/升级** — 必须记录理由和发起该变动的挑战者。

## 验证清单

- 每条最终 P0/P1/P2 发现都有证据和明确的触发路径。
- 每条发现都标注了可点击的代码位置（文件 + 行号区间）；无位置标注的发现不存在。
- 每个降级/驳回的攻击点都记录理由。
- 争议项在报告中可见，含双方立场和主 agent 的理由。
- 报告包含用户假设裁决和范围边界。
- 本 skill 未修改任何已提交/已暂存状态（只审不改）。
